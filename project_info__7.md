## Summary

CPay is a mobile-money payments gateway (collections, payouts, status checks, balances, callbacks, reconciliation, merchant self-service, finance/ops workflows) for MTN MoMo, Airtel Money, Airtel OpenAPI, Safaricom M-Pesa, and Yo! Payments. Two API generations run side-by-side: a frozen legacy `/api` + `/api/v1` surface and a signed/versioned `/api/v2/**` surface backed by an adapter/ledger/risk/compliance architecture.

**The single most important finding for planning:** the repository has advanced well past the state described in the earlier audit reports (project_info__1/2/3 at Flyway V30; project_info__4/5 at V32). On this checkout the code sits at **Flyway V35**, the **v2 OpenAPI contract is at version 1.5.0**, and the previously-flagged "highest-value remaining work" — maker-checker on finance close, settlement close, and payout approvals, plus the admin finance-close / payout-approval / settlement-close / webhook-ops UI screens — is **now implemented in code and wired into the admin portal navigation**. The residual gaps are concentrated in: (1) remaining UI surfaces (onboarding tracker, KYB review, certification dashboard, treasury dashboard), (2) OpenAPI/contract coverage for the newer endpoints, (3) an existing in-repo CitoConnect integration roadmap whose Phase 3–7 modules are not yet built, and (4) the long-standing structural poles (god-class decomposition, legacy provider monoliths, v1 money-path edge gaps).

## Architecture

**Pattern:** Layered modular monolith with an event-driven callback/claims subsystem and a plugin-style gateway adapter boundary.

```
Controllers → Services → Gateway adapters / Provider endpoint execution → JDBC repositories → MySQL 8 (Flyway V1..V35)
                 ↑                ↑
           Risk/ledger/     Callback queue (claim-based), webhooks,
           webhook seams     reconciliation, settlement, EFRIS, regulator reporting, schedulers
```

**Stack:**
- Backend: Spring Boot 4.1 (Spring Framework 7.x), Java 21, virtual threads on, Maven, MySQL 8, Flyway, Spring Session JDBC, ShedLock 7.7.0, Bucket4j 8.0.1, Apache POI 5.5.1, springdoc 3.0.3, Micrometer/Prometheus, Logstash logback, jul-to-slf4j. Base package `net.citotech.cito`.
- Frontend: React 18.3 + Vite 8, TypeScript (incremental, allowJs), TanStack Query v5, React Router v7, Tailwind 4, Vitest, own iOS-style `src/ui` design system. Dev server on :3000 proxies to :8081.
- Docs/SDK: `Docs/` (API contracts, ADRs, runbooks, readiness), `Sdk/` (Node/PHP/Python signing clients), `Integrations/Citoconnect/` (JS reference client). A full CitoConnect integration roadmap also exists in `Docs/Citoconnect-integration.md`.

**Execution start:**
1. `CpayadminApplication` → `StartupApplicationListener`, `SchedulerLockConfig`, `SecurityConfig`, `RestClientOutboundHttpExecutor.register()` (installs `Common.OutboundHttpExecutor`), `SslConfig`.
2. Requests land on legacy flat controllers (`Api`, `ApiV1Controller`, `TransactionsLogController`, `AdminsController`, …) or `/api/v2/**` (`PaymentsV2Controller`, `NativePaymentsV2Controller`, admin/compliance/reconciliation/payout/webhook/regulator controllers).
3. Scheduled work runs via `@Scheduled` + `@SchedulerLock` (ShedLock): `CallbackRetryScheduler`, `TransactionTimeoutScheduler`, `SettlementSweepScheduler`, `LedgerOperationsScheduler`, `OperationalDataCleanupScheduler`, `ReportingAggregateScheduler`, `InvoiceExpiryScheduler`, `FloatAlertScheduler`, `MerchantWebhookDeliveryScheduler`, `TransactionLogArchivalScheduler`, **`EfrisReceiptScheduler`**, plus the two money-movement crons in `TransactionsLogController`.
