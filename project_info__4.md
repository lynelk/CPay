## Summary

CPay is a mobile-money payments gateway (collections, payouts, status checks, balances, callbacks, reconciliation, merchant self-service, finance/ops workflows) for MTN MoMo, Airtel Money, Airtel OpenAPI, Safaricom M-Pesa, and Yo! Payments. Two API generations run side-by-side: legacy `/api`/`/api/v1` (must stay stable) and signed/versioned `/api/v2/**` backed by an adapter/ledger/risk architecture.

**Key finding for cost/speed planning:** the repository has advanced well past the state described in the attached prompt pack and the earlier audits (project_info__1/2/3 at Flyway V30). It now sits at **Flyway V32**, the **v2 OpenAPI contract is at version 1.5.0**, and **most of the 12 workstreams already have a working backend foundation**. The cost of "implement everything in the deck" is therefore much lower than the deck implies. The remaining work is concentrated in a smaller set of gaps: mostly UI surfaces, maker-checker approval enforcement, admin RBAC matrix, and hardening/verification rather than greenfield build.

## Cost & Speed Guidance — Recommended Implementation Order

The goal: maximize compliance/safety value per engineering dollar, and sequence work so each phase leaves the system in a more releaseable state.

### Phase 0 — Confirm what not to do (avoid double-paying)
~0 cost. Before planning, cross off these deck items as **already implemented on this checkout**:
- Refunds v2 (POST/GET `/api/v2/refunds`)
- Batch payout status + retry-failed (`/api/v2/batch-payouts/{id}/status`, `/retry-failed`)
- FX quotes + cross-border transfer intents
- Provider certification evidence + approval + coverage summary
- Webhook event catalog (versioned, schema-documented) + merchant self-service register/rotate/replay/log
- Sanctions/watchlist screening (hashed entries, BLOCK/REVIEW)
- KYC tiers + beneficial owners + documents + compliance profiles
- Compliance cases + risk-decision case capture
- Settlement batches + sweep + ledger posting
- Payout compensation saga (partial-reversal observability)
- Merchant RSA key encryption at rest (V31, `MerchantKeyEncryptionService`)
- TransactionStatus enum state machine (additive)
- Ops console real UI + TanStack hooks + webhook manager UI
- Full CI gate stack (backend verify + SBOM, migration uniqueness, OpenAPI presence, OWASP, CodeQL, frontend lint/test/typecheck/build, readiness docs)

### Phase 1 — Compliance/safety hardening (highest value per dollar)
**Estimated cost: ~1 developer-week per item.** These close the largest regulated-payment risks with the least surface area:

1. **Maker-checker on finance close + settlement close + manual match approve** (Workstream 6/7/3). The finance daily close and settlement batch close are currently single-actor writes (`FinanceWorkflowService.dailyClose`, `SettlementOpsService.closeBatch`). This is the single highest-risk gap for a regulated environment: "who approved what" is not provable. Cost is a state field + a second actor parameter + audit rows, not new architecture.
2. **Payout limit + approval workflow** (Workstream 7). Add daily/monthly/per-transaction/beneficiary-velocity limits + approval queue. The compensation saga and step-up MFA already exist; limits are the missing control.
3. **Webhook replay admin endpoint + test-callback button** (Workstream 5). Backend `replay(merchantId, deliveryId)` exists; expose an admin/merchant endpoint and a "test callback" action. Small, high-merchant-value.
4. **v1 idempotency/nonce/signing** (Workstream 12, D1). Legacy endpoints still lack idempotency. Given dual-path coexistence, this is a real safety gap but also the largest single refactor — **schedule it only after Phase 2**, because the compat path (PaymentOrchestrationService) already provides it for v2.

### Phase 2 — UI surfaces that unlock workflows (highest speed wins)
**Estimated cost: ~2–3 developer-weeks total across the four items.** The backend for KYB, certification, finance close, and settlement is done; what's missing is the ability for humans to use it. Each of these is a "wrap existing hooks/endpoints in a screen" task following the established `ModuleReconciliation.tsx`/`MerchantModuleWebhooks.tsx` pattern:

1. **Merchant onboarding tracker** (Workstream 2/10) — stepper over signup/email/KYB/channels/sandbox/callback/pricing/approval.
2. **Admin KYB review UI** (Workstream 2/9) — approve/reject/request-info on beneficial owners + documents + profiles.
3. **Finance daily-close dashboard** (Workstream 6/10) — statements received/unmatched/variance/approvals/close status.
4. **Provider certification dashboard** (Workstream 4/10) — scenario checklist per provider with evidence status.

### Phase 3 — API completeness + docs (moderate cost, high developer value)
**Estimated cost: ~1–2 developer-weeks.** Add the missing OpenAPI endpoints/schemas (webhooks events/replay, settlements list/statement, beneficiaries, compliance case decision), update the Postman collection, and write the consolidated developer guide + v1→v2 migration + sandbox guide. This is documentation + thin controller work.

### Phase 4 — Structural long-poles (only after 1–3, or as a separate funded track)
The high-effort items remain authentically open and are NOT cheap:
- **v1 money-path ledger unification + idempotency** (H/L) — dual-write `/api/v1` through `LegacyLedgerPostingService` + risk + reservation. The risk and ledger services already exist; the work is wiring + tests + migration.
- **God-class decomposition** (`TransactionsLogController` ~6,000+ lines, `Common` ~2,900) — deliberate, slow, regression-prone; do as a separate track, not part of feature work.
- **Beneficiaries, corridor reports, treasury positions** (Workstream 8 remainder) — only if cross-border is actually a product priority; otherwise defer.

## Final Recommendation

**Do not run all 12 workstreams.** The prompt pack was written against an earlier state of the repo; roughly 60–70% of its recommended work already exists in code. Running it verbatim would burn budget re-implementing finished features, missing the actual gaps.

The actual highest-value remaining work, in order:

1. **Maker-checker + audit on finance close, settlement close, and manual-match approve** (~1 dev-week) — closes the "who approved what" gap that the deck itself calls the #1 failure mode of payment systems. No new architecture; state + actor + audit.
2. **Payout limits + approval queue** (~1–1.5 dev-weeks) — risk controls for outbound money.
3. **Four UI surfaces** (onboarding tracker, KYB review, finance close dashboard, certification dashboard — ~2–3 dev-weeks total) — unlocks the completed backends for humans.
4. **Webhook replay admin endpoint + test-callback + OpenAPI for webhooks/settlements/beneficiaries/compliance decision** (~1 dev-week).
5. **Developer guide + migration + sandbox guide + curl examples** (~0.5–1 dev-week, can be parallelized with 3–4).
6. **Defer**: v1 idempotency/ledger unification and god-class decomposition to a dedicated follow-on track; beneficiaries/corridor-reports/treasury-position APIs only if cross-border is a confirmed product priority.

Rough cost estimate: **~6–9 developer-weeks** to close everything above using one developer, or ~3–4 weeks wall-clock with two parallel tracks (backend hardening ∥ frontend surfaces + docs). This is dramatically less than running the full 12-workstream deck, because the heavy lifting is already in the tree.
