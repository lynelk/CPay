## Summary

CPay is a mobile-money payments gateway (collections, payouts, status checks, balances, callbacks, reconciliation, merchant self-service, finance/ops workflows) for MTN MoMo, Airtel Money, Airtel OpenAPI, Safaricom M-Pesa, and Yo! Payments. Two API generations run side-by-side: a frozen legacy `/api` + `/api/v1` surface and a signed/versioned `/api/v2/**` surface backed by an adapter/ledger/risk/compliance architecture.

**The single most important finding for planning:** the repository has advanced well past the state described in the earlier audit reports (project_info__1/2/3 at Flyway V30; project_info__4/5 at V32). On this checkout the code sits at **Flyway V43**, the **v2 OpenAPI contract is at version 1.5.0**, and the previously-flagged "highest-value remaining work" — maker-checker on finance close, settlement close, and payout approvals, plus the admin finance-close / payout-approval / settlement-close / webhook-ops UI screens — plus the S5/S6 pilot surfaces (per-merchant feature registry, GnuGrid identity verification, payout-controls configuration, balance monitoring) are **now implemented in code and wired into the admin portal navigation**. Since the last update to this catalog, a full 15-slice billing-engine Phase 0/1 backlog also landed (`net.citotech.cito.billing`, `Docs/Adr/0003`-`0006`): tenant resolution, idempotent usage-event ingestion, a transactional outbox with retry/backoff (no consuming handler registered yet — an explicit, documented Phase 2 prerequisite), a read-only legacy fee-schedule price projection, MVP meter aggregation, and a reconciliation report — wired into exactly one live producer (`PaymentOrchestrationService.collect()`, behind a feature flag defaulting off). The residual gaps are concentrated in: (1) remaining UI surfaces (onboarding tracker, KYB review, certification dashboard, treasury dashboard, balance-monitoring dashboard), (2) OpenAPI/contract coverage for the newer endpoints, (3) an existing in-repo CitoConnect integration roadmap whose Phase 3–7 modules are not yet built, (4) the long-standing structural poles (god-class decomposition — still purely a plan doc, zero extraction started — legacy provider monoliths, v1 money-path edge gaps), and (5) billing-engine Phase 2 (real service cut-in: an outbox consumer, a working pricing engine, provider cost tracking, SMS/invoicing producers).

## Architecture

**Pattern:** Layered modular monolith with an event-driven callback/claims subsystem and a plugin-style gateway adapter boundary.

```
Controllers → Services → Gateway adapters / Provider endpoint execution → JDBC repositories → MySQL 8 (Flyway V1..V43)
                 ↑                ↑
           Risk/ledger/     Callback queue (claim-based), webhooks,
           webhook seams     reconciliation, settlement, EFRIS, regulator reporting, schedulers
```

**Stack:**
- Backend: Spring Boot 4.1 (Spring Framework 7.x), Java 21, virtual threads on, Maven, MySQL 8, Flyway, Spring Session JDBC, ShedLock 7.7.0, Bucket4j 8.0.1, Apache POI 5.5.1, springdoc 3.0.3, Micrometer/Prometheus, Logstash logback, jul-to-slf4j. Base package `net.citotech.cito`.
- Frontend: React 18.3 + Vite 8, TypeScript (incremental, allowJs), TanStack Query v5, React Router v7, Tailwind 4, Vitest, own iOS-style `src/ui` design system. Dev server on :3000 proxies to :8081.
- Docs/SDK: `Docs/` (API contracts, ADRs, runbooks, readiness), `Sdk/` (Node/PHP/Python signing clients), `Integrations/Citoconnect/` (JS reference client). A full CitoConnect integration roadmap also exists in `Docs/Citoconnect-integration.md`.

**Execution start:**
1. `CpayadminApplication` → `StartupApplicationListener`, `SchedulerLockConfig`, `SecurityConfig`, `RestClientOutboundHttpExecutor.register()` (installs `Common.OutboundHttpExecutor`), `SslConfig`.
2. Requests land on legacy flat controllers (`Api`, `ApiV1Controller`, `TransactionsLogController`, `AdminsController`, …) or `/api/v2/**` (`PaymentsV2Controller`, `NativePaymentsV2Controller`, admin/compliance/reconciliation/payout/webhook/regulator controllers).
3. Scheduled work runs via `@Scheduled` + `@SchedulerLock` (ShedLock): `CallbackRetryScheduler`, `TransactionTimeoutScheduler`, `SettlementSweepScheduler`, `LedgerOperationsScheduler`, `OperationalDataCleanupScheduler`, `ReportingAggregateScheduler`, `InvoiceExpiryScheduler`, `FloatAlertScheduler`, `MerchantWebhookDeliveryScheduler`, `TransactionLogArchivalScheduler`, **`EfrisReceiptScheduler`**, plus the two money-movement crons in `TransactionsLogController`.

## Key Abstractions (current)

### PayoutControlService (`payout/PayoutControlService.java`)
- **Responsibility:** configurable per-merchant/channel/currency/country payout limits (per-transaction, daily, monthly, beneficiary velocity) and a maker-checker approval queue. No control row ⇒ immediate execution (historical behavior preserved).
- **Key invariants:** approval row stores the original `PaymentRequest` payload; approval re-executes through `PaymentOrchestrationService.payout` (reservation + risk + provider + ledger + webhook) — money only ever moves through one tested path. Beneficiary counting reads `payer_number` (the legacy column the v2 orchestrator populates for payees), not `payee_number`, so velocity/first-beneficiary gates can't be silently bypassed.
- **Used by:** `PaymentsV2Controller.payout` (returns `APPROVAL_PENDING` 202 when parked), `PayoutApprovalController`.

### FinanceWorkflowService (`reconciliation/FinanceWorkflowService.java`)
- **Responsibility:** maker-checker daily close. `submitDailyClose` computes matched/unmatched/exception/variance, **rejects the submission up front when unmatched variance exceeds `finance_variance_tolerance_amount` (default 0 = fail closed)**, writes `PENDING_APPROVAL`. `approveDailyClose` requires a different actor and flips to `CLOSED`; `rejectDailyClose` records reason and keeps the row pending.
- **Invariant:** a CLOSED row is never re-opened (`ON DUPLICATE KEY UPDATE close_status=CASE WHEN close_status='CLOSED' THEN close_status ELSE 'PENDING_APPROVAL' END`).

### SettlementOpsService (`reconciliation/SettlementOpsService.java`)
- **Responsibility:** settlement batch lifecycle. `openBatch` posts the DR settlement-clearing / CR provider-float ledger entries (idempotent by `settlement:<reference>`); `requestBatchClose` → `PENDING_APPROVAL`; `approveBatchClose` / `rejectBatchClose` enforce maker≠checker in the UPDATE predicate itself.

### RiskDecisionService (`compliance/RiskDecisionService.java`)
- **Responsibility:** authorization-time risk engine: blocklist → sanctions screening → single-transaction cap → **payer velocity (new)** → daily merchant cap. Rules live in `risk_rules` with MERCHANT > TIER > GLOBAL precedence; KYC tier resolved from `compliance_profiles`.
- **Used by:** `PaymentOrchestrationService`, cross-border transfer intents, legacy portal payin via `RiskDecisionRegistry`.

### EfrisReceiptService (`efris/EfrisReceiptService.java`)
- **Responsibility:** EFRIS e-receipt outbox for successful UGX payins. Persists only the SHA-256 hash of the payer MSISDN; raw number is read back from the ledger in-process at delivery time only. Backfill sweep + exponential backoff (5 attempts) mirror the webhook delivery pattern.
- **Quirk:** uses `java.util.logging` rather than SLF4J (minor inconsistency with the rest of the app).

### RegulatorReportingService (`reporting/RegulatorReportingService.java`)
- **Responsibility:** BoU daily cash-flow report aggregated from `merchant_transactions_log` (counts + amounts only, no PII), idempotently upserted into `regulator_reports`; CSV derived from stored JSON at download time; PII inventory catalog endpoint.

### ModuleFinanceClose / ModulePayoutApprovals / ModuleSettlementClose / ModuleWebhookOps (frontend)
- All four are typed React function components on TanStack hooks with loading/error/empty states, loader sync, refresh-signal handling, and 401 → sessionExpired routing. They implement the maker/checker actor fields client-side, with the server enforcing maker≠checker.

### TreasuryPositionService (`crossborder/TreasuryPositionService.java`)
- **Responsibility:** read-side view over `treasury_positions` (V12) — available/reserved/net-available per currency. Write side stays in `CrossBorderTransferService` and the payout reservation paths.

## Data Flow (current, key paths)

### v2 payout with limit controls (the new gate)
1. Merchant POSTs `/api/v2/payments/payout` (signed, nonce).
2. `V2RequestSecurityService.verify()` → idempotency check.
3. **`PayoutControlService.evaluate(...)`** — if a control row exists and a limit/velocity/first-beneficiary trigger fires, the payout is parked: `payout_approval_queue` row (PENDING_APPROVAL, full payload JSON stored) + `PaymentResult{status:"APPROVAL_PENDING"}` 202 returned.
4. Admin opens `Payout Approvals` screen → selects row → enters checker actor → `POST /api/v2/admin/payout-approvals/{id}/approve`.
5. `PayoutApprovalController` flips the row to APPROVED (maker≠checker), then re-invokes `PaymentOrchestrationService.payout(request, merchant, "admin-approval")` — reservation → risk → `Common.doPayOut` → ledger posting → webhook.
6. Risk BLOCK still throws during re-execution; an approval can never bypass a hard risk decision.

### Finance daily close (maker-checker)
1. `ModuleFinanceClose` → `POST /api/v2/admin/recon-finance/close?date=&currency=&submittedBy=maker`.
2. `FinanceWorkflowService.submitDailyClose` computes summary; if unmatched variance > tolerance (default 0) → reject with `PaymentGatewayException`; else row `PENDING_APPROVAL`.
3. Checker → `POST /close/approve?approvedBy=` (different actor) → `CLOSED`, audited via `AdminAuditService` (`DAILY_CLOSE_APPROVE`).

### EFRIS e-receipt
1. A UGX payin resolves SUCCESSFUL (v2 orchestrator or legacy callback scan).
2. `EfrisReceiptScheduler` (ShedLock) → `enqueueMissingSuccessfulPayins(7, 500)` backfills the outbox for successful UGX payins missing a row; only `payer_msisdn_hash` is persisted.
3. `deliverDue(100)` POSTs pending receipts to the configured `cpay.efris.endpoint` with 5-attempt backoff; 2xx → SENT, else PENDING (retry) / FAILED.

### Admin webhook verification (test callback)
1. `ModuleWebhookOps` loads endpoints for a merchant (`GET /api/v2/admin/webhooks/merchants/{id}`).
2. "Queue test event" → `POST /api/v2/admin/webhooks/merchants/{id}/test-callback?eventType=payment.completed`.
3. `MerchantWebhookService.testCallback` queues a synthetic TEST event to the merchant's active endpoint(s); delivery is observable in the delivery log end-to-end. Audited (`WEBHOOK_TEST_CALLBACK`).
