## Summary

CPay is a mobile-money payments gateway (collections, payouts, status checks, balances, callbacks, reconciliation, merchant self-service, finance/ops workflows) for MTN MoMo, Airtel Money, Airtel OpenAPI, Safaricom M-Pesa, and Yo! Payments. The requested plan asks CPay to become a **domain-oriented modular monolith** with nine domains: Home, Payments & Transactions, KYC & Customer Mgt, Billing, Communication, Developers & Integrations, Operations, Administration, and Platform Core. The headline addition is **Communication as a first-class platform module** (SMS + WhatsApp + USSD + email, templates, campaigns, consent, delivery/retry, usage/billing).

**The gap analysis is now concrete.** The codebase has already absorbed much of the plan's Payments/KYC/Billing/Operations/Administration content — the double-entry ledger, reconciliation with maker-checker close, payout controls with approval queue, an actual billing engine (tenancy → usage → outbox → pricing → rated charges → invoices → completeness gate, V38–V49), KYC/risk/compliance, feature flags, and admin RBAC. What the plan's domain model maps to is a series of **small, well-defined extraction packages** plus one genuinely **large new module (Communication)**. The single most important finding for planning: **no `communication/` package exists at all today** — SMS remains a legacy utility (`Model/SmsGateway`, `TransactionsLogController.saveSms`/`testSendPendingSmsCron`), email is an empty interface (`EmailService.java` is a bare `interface EmailService {}`), and there is no WhatsApp/USSD/template/campaign/preferences code anywhere in the tree.

## Architecture

**Pattern today:** Layered modular monolith with an event-driven callback/claims subsystem, a plugin-style gateway adapter boundary, a transactional outbox (billing), and maker-checker approval workflows. This is already the plan's preferred pattern; what's missing is the **domain packaging layer** (the plan's `net.citotech.cpay.{home,payments,customer,billing,communication,integration,operations,administration,platform}` target).

```
Controllers → Services → Gateway adapters / Provider endpoint execution → JDBC repositories → MySQL 8 (Flyway V1..V49)
                 ↑                ↑
           Risk/ledger/     Callback queue (claim-based), webhooks,
           webhook seams     reconciliation, settlement, EFRIS, regulator reporting, billing outbox, schedulers
```

**Stack:**
- Backend: Spring Boot 4.1 (Spring Framework 7.x), Java 21, Maven, MySQL 8, Flyway (V1–V49), Spring Session JDBC, ShedLock 7.7.0, Bucket4j 8.0.1, Apache POI 5.5.1, springdoc 3.0.3, Micrometer/Prometheus, Logstash logback, jul-to-slf4j. Base package is `net.citotech.cito` (the plan's target `net.citotech.cpay` is **not** the current base package).
- Frontend: React 18.3 + Vite 8, TypeScript (incremental, allowJs), TanStack Query v5, React Router v7, Tailwind 4, Vitest, own iOS-style `src/ui` design system. Dev server on :3000 proxies to :8081.
- Docs/SDK: `Docs/` (API contracts, ADRs, runbooks, readiness), `Sdk/` (Node/PHP/Python signing clients), `Integrations/Citoconnect/` (JS reference client).

**Execution start:**
1. `CpayadminApplication` → `StartupApplicationListener`, `SchedulerLockConfig`, `SecurityConfig`, `RestClientOutboundHttpExecutor.register()`, `SslConfig`.
2. Requests land on legacy flat controllers (`Api`, `ApiV1Controller`, `TransactionsLogController`, `AdminsController`, …) or `/api/v2/**` (`PaymentsV2Controller`, `NativePaymentsV2Controller`, admin/compliance/reconciliation/payout/webhook/regulator controllers).
3. Scheduled work runs via `@Scheduled` + `@SchedulerLock` (ShedLock): `CallbackRetryScheduler`, `TransactionTimeoutScheduler`, `SettlementSweepScheduler`, `LedgerOperationsScheduler`, `OperationalDataCleanupScheduler`, `ReportingAggregateScheduler`, `InvoiceExpiryScheduler`, `FloatAlertScheduler`, `MerchantWebhookDeliveryScheduler`, `TransactionLogArchivalScheduler`, `EfrisReceiptScheduler`, `OutboxRelay` — plus two money-movement crons in `TransactionsLogController` (`testCheckstatusCron`, `paymentsPayCron`).

## Section-by-Section Evaluation of the Attached Plan

The plan (26 sections) is evaluated against what exists in code today. Each section is marked ✅ (already largely satisfied), 🔶 (partially satisfied / needs a bridge), or ❌ (not started / no equivalent exists).

### §1–2. Domain objective & Home domain — 🔶
- The plan's modular-monolith intent is already the de-facto architecture (layered, single deployable). The **domain package naming** (`net.citotech.cpay.{domain}`) is not — the base package remains `net.citotech.cito`.
- **Home**: partially exists as `TransactionsLogController` dashboard endpoints (`/transactions/getDashboardDetailsPayinsVsPayouts`, `...TxPerGateway`, `...TransactionTypes`, `...TxVolumes`, `...NetworkBalances`) — but these are **still inside the god-class controller**, read directly off the transactional `merchant_transactions_log` table, and do **not** use the `reporting_aggregates` tables (V27 `ReportingAggregateService` exists and is unused by the dashboard). No dedicated `home/` package exists.

### §3. Payments & Transactions — 🔶 (structure exists; packaging and state machine don't)
- **Payment Operations**: `PaymentOrchestrationService` is the matured "Payment Application Service" (risk → gateway → ledger → webhook). Collections/payouts/batch/approval/risk all have real code: `batch/`, `payout/` (controls + approvals), `compliance/` (risk + KYC), `refund/` (`RefundService`, `RefundStatus`).
- **Funds & Settlement**: `ledger/` (`DoubleEntryLedgerService`, `LegacyLedgerPostingService`, `LegacyLedgerRepairService`, `LedgerBalanceService`, `TrialBalanceResult`), `crossborder/` (treasury positions, FX quotes), `balance/` (authoritative balances, balance view read models, channel balances, float balance reader, balance monitoring), `reconciliation/` (settlement scheduling + maker-checker close).
- **Reconciliation & Close**: fully implemented (`reconciliation/` package: parsers for MTN/Airtel/Airtel OpenAPI/Safaricom/Yo!, import/validate/match, `ReconService`, `FinanceWorkflowService` with variance-tolerance gate + maker-checker, `SettlementOpsService`).
- **What's missing vs. plan**: (a) the plan's package layout (`payments/transaction`, `payments/collection`, `payments/payout`, `payments/funds`, `payments/reconciliation`) is not the current layout — logic is spread across `net.citotech.cito` root + peer packages; (b) **no canonical payment state machine** — `TransactionStatus` strings are free-form (`PENDING/SUCCESSFUL/FAILED/UNDETERMINED`); a `Model/TransactionStatus.java` exists but is not a governing enum; (c) the plan's "approval queue" exists for payouts (`payout_approval_queue`, V34) and finance close, but not for transactions generally; (d) **no unified v1/v2 engine** — `PaymentOrchestrationService` is v2-compat; the raw v1 paths (`Api.java`, `ApiV1Controller`, legacy `Common.doPayIn/doPayOut`) still run separate code that has now been given ledger+risk parity but is not the same engine.

### §4. KYC & Customer Mgt — 🔶
- Real code exists: `compliance/KycService` (beneficial owners + KYC documents), `compliance/ComplianceCaseService`, `compliance/RiskDecisionService` (blocklist, sanctions screening, single-transaction/daily caps, **payer velocity**, **KYC-tier caps**), `compliance/KycController`, `merchant/` (signup, channel configuration, email verification, notification preferences, team roles via V23), `identity/` (GnuGrid NIN pilot, V37).
- **What's missing vs. plan**: (a) the `customer/` domain package with profile/onboarding/readiness/team sub-packages; (b) **no explicit customer lifecycle state machine** (REGISTERED → EMAIL_VERIFIED → PROFILE_COMPLETE → KYC_SUBMITTED → KYC_REVIEW → APPROVED → INTEGRATION_SETUP → TESTING → GO_LIVE_APPROVAL → LIVE); readiness is computed by `ReadinessDashboardService` (platform + per-merchant checklists) but there is no transitioned-state flow; (c) **no KYB/onboarding review UI** — `KycService`/`ComplianceCaseService` backends exist, no admin screen; (d) `MerchantNotificationPreferenceService` exists — this is the seed of the plan's consent/preferences model.

### §5. Billing — ✅ (the single most complete match to the plan)
- The plan's `billing/catalog|plan|pricing|metering|rating|charge|invoice|credit|payment|revenue|cost` maps almost 1:1 to the existing `billing/` package:
  - `billing/tenancy/` — tenant resolution (`BillingTenantResolver`, V38)
  - `billing/usage/` — idempotent usage events (`UsageGatewayService`, `UsageEventOutboxHandler`, V40)
  - `billing/outbox/` — classic transactional outbox (`OutboxWriter`, `OutboxRelay`, 3 handlers, V41; ADR 0005)
  - `billing/pricing/` — real rating engine (`RatingEngine`, `TierCalculator` (genuine marginal tier math), `PriceResolver`, `PriceBookAuthoringService`, `RatedChargeOutboxHandler`, V43/V44)
  - `billing/metering/` — `MeterAggregationService` (COUNT/SUM with JSON dimension filter, V39)
  - `billing/invoicing/` — draft invoices + charge staging (`BillingInvoiceService`, V47) + completeness gate (`BillingCompletenessGateService`, V49)
  - `billing/cost/` — `ProviderCostOutboxHandler` (reuses the same `RatingEngine` against `charge_type='PROVIDER_COST'`)
  - `billing/integration/cpay/` — `PaymentUsageOutboxHook` (the single hook in both collection and payout), `BillingLedgerLinkWriter` + `BillingLedgerAccountTemplateService` (ADR 0004), `LegacyFeeSchedulePriceAdapter`
  - `billing/reconciliation/` — `UsagePaymentReconciliationService` (Phase-1 exit criterion)
- **What's missing vs. plan**: (a) the plan's `billing/credit`, `billing/revenue`, `billing/catalog`, `billing/plan` sub-packages don't exist as named packages (credit notes table exists, V48); (b) **no billing payment/collection onto invoices** (an invoice is DRAFT → completeness gate → FINALIZED; paying an invoice and updating the ledger from that payment is a separate, later slice); (c) **no Communication-metering producer** (the plan's §6.10 SMS/WhatsApp/USSD/email usage → billing meter pipeline has no source events because Communication doesn't exist yet); (d) the billing engine is gated behind feature flags (`billing-usage-outbox`, default off) and only wired to `PaymentOrchestrationService`.

## The Communication Module Design (what to build — concrete)

Because the plan's most significant gap is Communication, here is the concrete extraction/build sequence grounded in the existing codebase patterns (mirroring `gateway/PaymentChannelAdapter`, `callback/CallbackTaskService`, `billing/outbox`, and `webhook/MerchantWebhookService`, all of which exist and can be borrowed):

**Extract (P0.5 — behavior-preserving):**
1. `Model/SmsGateway.java` → `communication/sms/SmsGatewayAdapter.java` (keep settings-driven HTTP behavior; add a `CommunicationChannelAdapter` interface).
2. The SMS delivery cron `TransactionsLogController.testSendPendingSmsCron` → `communication/delivery/SmsDeliveryWorker` (move the `merchant_sms` table reads/writes + statement charge/reversal logic; keep the file lock, add `@SchedulerLock` to match the other schedulers).
3. `TransactionsLogController.saveSms` / `getMerchantSms` / `buySms` / `cancelSms` → `communication/` (service + controller thin adapter).
4. `Common.DB_TABLE_MERCHANT_SMS` constant usage → repository class.

**Build (P0.6/P1.5/P1.6):**
5. `communication/CommunicationService` — the plan's provider-neutral entry point (recipient + template + channels + context).
6. `communication/ChannelRouter` — preference/consent + channel availability → route.
7. `communication/ChannelAdapter` contract — `capabilities()/send()/status()/verifyCallback()/health()` mirroring `PaymentChannelAdapter`.
8. `communication/template/` — `TemplateService` + `TemplateRepository` (categories: Transaction/KYC/Billing/Security/Operations/Marketing/Customer Service; channel/language/version/active state/variables).
9. `communication/preference/` — `ConsentService`, `OptOutService`, `NotificationPreferenceService` (schema table `communication_preferences` per plan §6.9; seed from existing `merchant_notification_preferences` V22).
10. `communication/delivery/` — `DeliveryQueue`, `DeliveryWorker`, `RetryPolicy`, `DeliveryLogRepository` (mirror `MerchantWebhookService` delivery log + replay).
11. `communication/whatsapp/`, `communication/ussd/` — adapters + session/menu engine (USSD calls the same application services as web/API; a `UssdSessionService` + `UssdMenuService` with no payment-rule duplication).
12. `communication/campaign/` — `CampaignService`, `AudienceService`, `CampaignScheduler` (reuse `@SchedulerLock` pattern).
13. Communication → Billing metering (P1.7): emit `billing_usage_events` `COMMUNICATION_SMS_SENT`, `COMMUNICATION_WHATSAPP_CONVERSATION`, `COMMUNICATION_USSD_SESSION`, `COMMUNICATION_EMAIL_DELIVERED` via the existing `UsageGatewayService.recordUsage(...)` (idempotent by key) — this is a one-line wiring into the existing idempotency path.
14. Transactional events: add a domain-event seam in `PaymentOrchestrationService` (after `Common.doPayIn`/`captureReservation` — right where `PaymentUsageOutboxHook` and `queueWebhook` already fire) that emits the plan's `payment.created/pending/successful/failed`, `payout.approval_required/successful`, `refund.completed`, `settlement.completed`, `invoice.created`, `invoice.overdue`, `kyc.*`, `account.live`; Communication subscribes via a `CommunicationPolicy` → template → preference → router pipeline (§6.5). Initially in-process (the plan explicitly allows this); the billing outbox is the pattern to copy for durability.

## Data Flow (current, key paths)

### v2 payout with limit controls
1. Merchant POSTs `/api/v2/payments/payout` (signed, nonce) → `V2RequestSecurityService.verify()` → idempotency check.
2. `PayoutControlService.evaluate(...)` — if a limit/velocity/first-beneficiary trigger fires, the payout is parked: `payout_approval_queue` row (PENDING_APPROVAL, full payload JSON stored) + `PaymentResult{status:"APPROVAL_PENDING"}` 202.
3. Admin opens `Payout Approvals` → checker → `POST /api/v2/admin/payout-approvals/{id}/approve` (maker≠checker enforced).
4. `PaymentOrchestrationService.payout` re-executes: reservation → risk → `Common.doPayOut` → ledger posting → webhook → `PaymentUsageOutboxHook`.
5. Risk BLOCK still throws during re-execution; approval can never bypass a hard risk decision.

### Billing pipeline (the plan's §5 pipeline is real)
1. `PaymentOrchestrationService.collect()`/`.payout()` → `PaymentUsageOutboxHook.recordPaymentCollected/Submitted` (feature flag `billing-usage-outbox`).
2. `OutboxWriter.write(...)` inserts a `billing_outbox` row inside the caller's transaction.
3. `OutboxRelay` (ShedLock) polls → dispatches to **every** matching handler: `UsageEventOutboxHandler` (writes `billing_usage_events`, idempotent by `idempotency_key`), `RatedChargeOutboxHandler` (computes `billing_rated_charges` via `RatingEngine`), `ProviderCostOutboxHandler` (same engine, `charge_type='PROVIDER_COST'`).
4. `MeterAggregationService` aggregates; `BillingCompletenessGateService` + `BillingInvoiceService` stage DRAFT invoices (V47) → completeness gate (V49, maker-checker, checker-waiver path).

### SMS today (the legacy path Communication will absorb)
1. Merchant portal `saveSms` → `merchant_sms` row (PENDING) + statement charge recorded.
2. `testSendPendingSmsCron` (file-locked, NOT `@SchedulerLock`) pulls up to 1000 PENDING SMS rows.
3. For each: charge the merchant's SMS balance (DR) → call the settings-driven SMS HTTP gateway (`sms_api_url` + template params) → 2xx = SENT, non-2xx = REJECTED (charge reversed, per audit P5), transport failure = FAILED (charge reversed), → update `merchant_sms` row.
4. No template engine, no channel routing, no consent, no delivery log, no retry, no WhatsApp/USSD/email.

## Non-Obvious Behaviors & Design Decisions

- **Two engine generations with parity, not unity**: `Common.doPayIn/doPayOut` and `PaymentOrchestrationService` both run risk (`RiskDecisionRegistry`/`RiskDecisionService`) and post ledger entries (`LegacyLedgerPostingService`/`DoubleEntryLedgerService`). v1 and v2 are behaviorally aligned but structurally separate — the plan's "one domain engine" (DoD #6) is a real refactor, not a rename.
- **The `skipRiskCheck` seam**: `Common.doPayIn/doPayOut` run risk unless called with `skipRiskCheck=true`; `PaymentOrchestrationService` runs its own risk first and must call the overload to avoid duplicate `risk_decisions` rows. Any new money-movement caller must understand this.
- **Statement/ledger dual-write on the legacy path**: the legacy cron (`testCheckstatusCron`) writes per-balance-column statement rows (MTN/Airtel/Safaricom/SMS, single-row `merchant_statement` running balance) **and** `LegacyLedgerPostingService` posts double-entry rows. The ledger is the canonical source of truth (ADR 0002); `merchant_statement` is a legacy read model with `Double` arithmetic (audit A1/B1/A8 fixes keep the ledger authoritative).
- **ShedLock is the cross-instance guard; file locks remain as defense-in-depth**: all `@Scheduled` jobs have `@SchedulerLock`; the two money-movement crons and the SMS cron still carry the old `java.nio.channels.FileLock` (documented in-code as redundant-but-harmless). The SMS cron is the **only** active scheduled delivery worker that lacks `@SchedulerLock` — a multi-instance deployment can currently double-send SMS (two instances each pulling the same PENDING rows). This is a concrete, high-priority fix when extracting Communication (the plan's P0.5).
- **SMS billing is statement-based, not engine-based**: `buySms` debits a merchant's gateway balance and credits an `sms_balance` column; `testSendPendingSmsCron` charges `merchant_statement` rows per SMS and reverses on failure. The billing engine (`billing/`) has no visibility of SMS usage at all — the plan's §6.10 Communication→Billing meter pipeline is the bridge.
- **Email is literally an empty interface**: `EmailService.java` is `interface EmailService {}`. Any plan work that assumes email capability must account for this (only Spring Mail `SendMail`/`MerchantEmailVerificationService` exist for verification emails).
- **Dashboards read the transactional table**: all six dashboard chart endpoints query `merchant_transactions_log` directly; `reporting_aggregates` (V27) exists but is unused by them. Home domain extraction (plan §2) is also a performance fix.
- **Feature flags gate the billing engine**: `billing-usage-outbox` defaults off globally, per-merchant override via `merchant_feature_flags` (V36). Billing is real but not yet on by default.
- **Maker-checker is actor-difference, not role-difference**: every finance/payout/settlement approval requires a *different admin* but any two admins qualify. The plan's ISO/IEC 27001 §17 and Administration domain would eventually want role-segregated checkers.
- **Free-string transaction statuses**: `PENDING/SUCCESSFUL/FAILED/UNDETERMINED` (plus batch `PROCESSING/PAUSED/STOPPED/DONE`) are string literals across controllers/services. `Model/TransactionStatus.java` exists but is not the governing enum. The plan's state machine (DoD #8) is additive and large.
- **PII-safe patterns to copy**: EFRIS (V35) stores only SHA-256 payer MSISDN hashes; identity (V37) stores NIN/name/MSISDN as hashes + masks; `PiiMasking` masks high-traffic logs. Communication must apply the same to recipients/content.
- **Live financial periods can be locked**: V46 `ledger_period_locks` lets an operator block new ledger postings for a currency during a date range (fail-open by default) so trial-balance snapshots aren't invalidated mid-calculation.
- **Invoice completeness gate allows checker waivers**: V49's `billing_completeness_gates` stores the automated PASS/FAIL at submit time; a checker may approve a FAIL with a `waiver_reason` (explicitly the "checker-waiver" path named in the billing plan).

## Key Abstractions (current — the building blocks the refactor extends)

### PaymentChannelAdapter (`gateway/PaymentChannelAdapter.java`)
- **Responsibility**: the plugin boundary every payment provider implements — `capabilities()`, `collect()`, `payout()`, `status()`, `balance()`, `verifyCallback()`, `health()`.
- **Used by**: `PaymentChannelRegistry`, `GatewayExecutionService`, `ProviderEndpointExecutionService`, `ChannelRoutingService`. **This is the exact template for the plan's `CommunicationChannelAdapter` (§8).**

### MerchantWebhookService (`webhook/MerchantWebhookService.java`)
- **Responsibility**: enqueue/deliver/retry/replay webhook events to merchant endpoints; delivery log with per-attempt detail; secret rotation; test-callback. **This is the template for the plan's Communication delivery queue (retry policy, delivery logs, callback verification).**

### OutboxWriter / OutboxRelay (`billing/outbox/`)
- **Responsibility**: transactional outbox (ADR 0005) — `OutboxWriter.write` joins the caller's transaction; `OutboxRelay` (ShedLock) dispatches each row to every matching `OutboxEventHandler` with exponential backoff and poison-message → FAILED. **This is the template for any durable Communication event pipeline (§16) and already feeds the billing meter.**

### RatingEngine / TierCalculator (`billing/pricing/`)
- **Responsibility**: real graduated/marginal tier math and flat/percentage/tier/minimum/maximum price components into one rated charge (HALF_UP scale 2). **Communication usage metering reuses `UsageGatewayService` + this engine with zero new pricing code.**

### BillingCompletenessGateService (`billing/reconciliation/BillingCompletenessGateService.java`)
- **Responsibility**: maker-checker gate a DRAFT invoice must pass to become FINALIZED; stores automated PASS/FAIL at submit; checker can approve a FAIL with `waiver_reason`. **The newest maker-checker pattern; the same shape would back an ISO-20000 change/approval workflow (§9/§19).**

### FinanceWorkflowService / SettlementOpsService / PayoutControlService
- **Responsibility**: maker-checker daily close (variance-tolerance gate, fail-closed default), settlement batch close, payout limit controls + approval queue. **These are the plan's §3 approval/close patterns — complete.**

### Reading the plan's "sizes": the real work is Communication, then packaging/enforcement
The remaining slice sizes, estimated against actual code:

## Bottom Line

The attached ISO/domain plan is substantially **already implemented in spirit** for Payments (operations, funds, reconciliation & close), KYC/Customer (compliance risk, KYC docs, identity pilot), Billing (tenancy → usage → outbox → pricing → invoices → completeness gate, V38–V49), and Administration (RBAC-lite, audit chain, feature flags, maker-checker). The plan's Definition of Done #1–#6, #9, #13–#14 are fully or mostly met in behavior. What is genuinely **not** done:

1. **Communication as a first-class domain** (DoD #9–#12) — the plan's central addition. SMS is a legacy utility buried inside the transactions god-class; email is an empty interface; WhatsApp/USSD/templates/campaigns/consent/delivery-retry do not exist. This is the largest net-new build (~3–5+ dev-weeks for a solid core).
2. **Domain packaging** (DoD #1–#2) — `net.citotech.cito.{flat root}` → `net.citotech.cpay.{home,payments,customer,billing,communication,integration,operations,administration,platform}`; frontend `src/features/{domain}` + route-driven navigation (DoD #1).
3. **Architecture guardrail enforcement** (DoD #15) — ArchUnit rules for the plan's §21 dependency flow; zero cost today, prevents every future violation.
4. **One payment engine + state machine** (DoD #6, #8) — v1/v2 parity exists but not unity; statuses are free-form strings.
5. **Operations SLI/SLO + incident/problem + service catalogue** (DoD #16–#17) — the ISO/IEC 20000-1 home.
6. **Communication→Billing metering** (DoD #11) — the pipeline exists; it just has no Communication source events yet.

Recommended first moves (in order): land the ArchUnit guardrails (P0.1, 1 day); extract SMS into `communication/` with the `@SchedulerLock` fix (P0.5, fixes a real double-send bug); define `CommunicationChannelAdapter` + template/preference/delivery core (P0.6); then the frontend route-driven navigation (P0.3) and the payment state machine (P0.8) as the next slices. The Billing engine already proves the "do it once, domain-owned, outbox-backed" pattern the plan wants Communication to follow.
