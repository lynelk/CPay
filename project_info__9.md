## Summary

CPay is a mobile-money payments gateway (collections, payouts, status checks, balances, callbacks, reconciliation, merchant self-service, finance/ops workflows) for MTN MoMo, Airtel Money, Airtel OpenAPI, Safaricom M-Pesa, and Yo! Payments. The requested plan asks CPay to become a **domain-oriented modular monolith** with nine domains: Home, Payments & Transactions, KYC & Customer Mgt, Billing, Communication, Developers & Integrations, Operations, Administration, and Platform Core. The headline addition is **Communication as a first-class platform module** (SMS + WhatsApp + USSD + email, templates, campaigns, consent, delivery/retry, usage/billing).

**The gap analysis is now concrete.** The codebase has already absorbed much of the plan's Payments/KYC/Billing/Operations/Administration content — the double-entry ledger, reconciliation with maker-checker close, payout controls with approval queue, an actual billing engine (tenancy → usage → outbox → pricing → rated charges → invoices → completeness gate, V38–V49), KYC/risk/compliance, feature flags, and admin RBAC. What the plan's domain model maps to is a series of **small, well-defined extraction packages** plus one genuinely **large new module (Communication)**. The single most important finding for planning: **no `communication/` package exists at all today** — SMS remains a legacy utility (`Model/SmsGateway`, `TransactionsLogController.saveSms`/`testSendPendingSmsCron`), email is an empty interface (`EmailService.java` is a bare `interface EmailService {}`), and there is no WhatsApp/USSD/template/campaign/preferences code anywhere in the tree.

## Architecture

**Pattern today:** Layered modular monolith with an event-driven callback/claims subsystem, a plugin-style gateway adapter boundary, a transactional outbox (billing), and maker-checker approval workflows. This is already the plan's preferred pattern; what's missing is the **domain packaging layer** (the plan's `net.citotech.cpay.{home,payments,customer,billing,communication,integration,operations,administration,platform}` target).

```
Controllers → Services → Gateway adapters / Provider endpoint execution → JDBC repositories → MySQL 8 (Flyway V1..V49)
                 ↑                ↑
           Risk/ledger/     Callback queue (claim-based), webhooks,
           webhook seams     reconciliation, settlement, EFRIS, regulator reporting, billing outbox, schedulers
```

**Stack:**
- Backend: Spring Boot 4.1 (Spring Framework 7.x), Java 21, Maven, MySQL 8, Flyway (V1–V49), Spring Session JDBC, ShedLock 7.7.0, Bucket4j 8.0.1, Apache POI 5.5.1, springdoc 3.0.3, Micrometer/Prometheus, Logstash logback, jul-to-slf4j. Base package is `net.citotech.cito` (the plan's target `net.citotech.cpay` is **not** the current base package).
- Frontend: React 18.3 + Vite 8, TypeScript (incremental, allowJs), TanStack Query v5, React Router v7, Tailwind 4, Vitest, own iOS-style `src/ui` design system. Dev server on :3000 proxies to :8081.
- Docs/SDK: `Docs/` (API contracts, ADRs, runbooks, readiness), `Sdk/` (Node/PHP/Python signing clients), `Integrations/Citoconnect/` (JS reference client).

**Execution start:**
1. `CpayadminApplication` → `StartupApplicationListener`, `SchedulerLockConfig`, `SecurityConfig`, `RestClientOutboundHttpExecutor.register()`, `SslConfig`.
2. Requests land on legacy flat controllers (`Api`, `ApiV1Controller`, `TransactionsLogController`, `AdminsController`, …) or `/api/v2/**` (`PaymentsV2Controller`, `NativePaymentsV2Controller`, admin/compliance/reconciliation/payout/webhook/regulator controllers).
3. Scheduled work runs via `@Scheduled` + `@SchedulerLock` (ShedLock): `CallbackRetryScheduler`, `TransactionTimeoutScheduler`, `SettlementSweepScheduler`, `LedgerOperationsScheduler`, `OperationalDataCleanupScheduler`, `ReportingAggregateScheduler`, `InvoiceExpiryScheduler`, `FloatAlertScheduler`, `MerchantWebhookDeliveryScheduler`, `TransactionLogArchivalScheduler`, `EfrisReceiptScheduler`, `OutboxRelay` — plus two money-movement crons in `TransactionsLogController` (`testCheckstatusCron`, `paymentsPayCron`).

Collections/payouts/batch/approval/risk all have real code: `batch/`, `payout/` (controls + approvals), `compliance/` (risk + KYC), `refund/` (`RefundService`, `RefundStatus`).

## Data Flow (current, key paths)

### v2 payout with limit controls
1. Merchant POSTs `/api/v2/payments/payout` (signed, nonce) → `V2RequestSecurityService.verify()` → idempotency check.
2. `PayoutControlService.evaluate(...)` — if a limit/velocity/first-beneficiary trigger fires → parked: `payout_approval_queue` (PENDING_APPROVAL, full payload JSON) + `PaymentResult{status:"APPROVAL_PENDING"}` 202.
3. Admin → `POST /api/v2/admin/payout-approvals/{id}/approve` (maker≠checker enforced).
4. `PaymentOrchestrationService.payout` re-executes: reservation → risk → `Common.doPayOut` → ledger posting → webhook → `PaymentUsageOutboxHook`.
5. Risk BLOCK still throws during re-execution; approval cannot bypass a hard risk decision.

### Billing pipeline (the plan's §5 pipeline is real)
1. `PaymentOrchestrationService.collect()/.payout()` → `PaymentUsageOutboxHook` (flag `billing-usage-outbox`).
2. `OutboxWriter.write(...)` inserts a `billing_outbox` row inside the caller's transaction.
3. `OutboxRelay` (ShedLock) → dispatches to **every** matching handler: `UsageEventOutboxHandler` (idempotent `billing_usage_events`), `RatedChargeOutboxHandler` (`RatingEngine` → `billing_rated_charges`), `ProviderCostOutboxHandler` (`charge_type='PROVIDER_COST'`).
4. `MeterAggregationService` aggregates; `BillingCompletenessGateService` + `BillingInvoiceService` stage DRAFT invoices (V47) → completeness gate (V49, maker-checker, checker-waiver path).

### SMS today (the legacy path Communication will absorb)
1. Merchant portal `saveSms` → `merchant_sms` row (PENDING) + statement charge recorded.
2. `testSendPendingSmsCron` (file-locked, NOT `@SchedulerLock`) pulls up to 1000 PENDING rows.
3. For each: DR the merchant's SMS balance → settings-driven HTTP SMS gateway call → 2xx = SENT, non-2xx = REJECTED (charge reversed, audit P5), transport failure = FAILED (charge reversed) → update row.
4. No templates, no routing, no consent, no delivery log, no retry, no WhatsApp/USSD/email.

## Non-Obvious Behaviors & Design Decisions

- **Two engine generations with parity, not unity**: `Common.doPayIn/doPayOut` and `PaymentOrchestrationService` both run risk and post ledger entries. v1 and v2 are behaviorally aligned but structurally separate — the plan's "one domain engine" (DoD #6) is a real refactor, not a rename.
- **The `skipRiskCheck` seam**: `Common.doPayIn/doPayOut` run risk unless called with `skipRiskCheck=true`; `PaymentOrchestrationService` runs its own risk first and must use the overload to avoid duplicate `risk_decisions` rows. Any new money-movement caller must understand this.
- **Statement/ledger dual-write on the legacy path**: the legacy cron writes per-balance-column statement rows *and* `LegacyLedgerPostingService` posts double-entry rows. The ledger is canonical (ADR 0002); `merchant_statement` is a legacy read model with `Double` arithmetic.
- **ShedLock is the cross-instance guard; file locks remain as defense-in-depth**: all `@Scheduled` jobs have `@SchedulerLock`; the two money-movement crons and the SMS cron still carry old file locks. **The SMS cron is the only active scheduled delivery worker without `@SchedulerLock` — a multi-instance deployment can currently double-send SMS.** High-priority fix when extracting Communication.
- **SMS billing is statement-based, not engine-based**: `buySms` debits a gateway balance and credits an `sms_balance` column; the delivery cron charges `merchant_statement` and reverses on failure. The billing engine has no visibility of SMS usage — the §6.10 bridge is net-new.
- **Email is literally an empty interface**: `EmailService.java` is `interface EmailService {}`. Any plan work assuming email capability must account for this.
- **Dashboards read the transactional table**: all six chart endpoints query `merchant_transactions_log` directly; `reporting_aggregates` (V27) exists but is unused. Home-domain extraction is also a performance fix.
- **Feature flags gate the billing engine**: `billing-usage-outbox` defaults off globally, per-merchant override via `merchant_feature_flags` (V36).
- **Maker-checker is actor-difference, not role-difference**: requires a *different admin*, but any two admins qualify. ISO-27001 Administration work would want role-segregated checkers.
- **Free-string transaction statuses**: `PENDING/SUCCESSFUL/FAILED/UNDETERMINED` (+ batch states) are string literals across services; `Model/TransactionStatus.java` exists but is not governing.
- **PII-safe patterns to copy**: EFRIS (V35) stores only SHA-256 payer MSISDN hashes; identity (V37) stores NIN/name/MSISDN as hashes + masks; `PiiMasking` masks high-traffic logs. Communication must apply the same to recipients/content.
- **Live financial periods can be locked**: V46 `ledger_period_locks` lets operators block postings per currency/date (fail-open) so trial-balance snapshots aren't invalidated mid-calculation.
- **Invoice completeness gate allows checker waivers**: V49 stores the automated PASS/FAIL at submit; a checker may approve a FAIL with `waiver_reason` — explicitly the "checker-waiver" path.

## Key Abstractions (current — the building blocks the refactor extends)

### PaymentChannelAdapter (`gateway/PaymentChannelAdapter.java`)
- **Responsibility**: the plugin boundary every payment provider implements — `capabilities()`, `collect()`, `payout()`, `status()`, `balance()`, `verifyCallback()`, `health()`.
- **Used by**: `PaymentChannelRegistry`, `GatewayExecutionService`, `ProviderEndpointExecutionService`, `ChannelRoutingService`. **This is the exact template for the plan's `CommunicationChannelAdapter` (§8).**

### MerchantWebhookService (`webhook/MerchantWebhookService.java`)
- **Responsibility**: enqueue/deliver/retry/replay webhook events; delivery log with per-attempt detail; secret rotation; test-callback. **Template for the plan's Communication delivery queue.**

### OutboxWriter / OutboxRelay (`billing/outbox/`)
- **Responsibility**: transactional outbox (ADR 0005) — joins the caller's transaction; ShedLock poller dispatches to every matching handler with exponential backoff, poison → FAILED. **Template for any durable Communication event pipeline; already feeds the billing meter.**

### RatingEngine / TierCalculator (`billing/pricing/`)
- **Responsibility**: real graduated/marginal tier math and flat/percentage/tier/minimum/maximum components into one rated charge (HALF_UP scale 2). **Communication usage metering reuses `UsageGatewayService` + this engine with zero new pricing code.**

### BillingCompletenessGateService (`billing/reconciliation/`)
- **Responsibility**: maker-checker gate a DRAFT invoice must pass to become FINALIZED; stores automated PASS/FAIL; checker can approve a FAIL with `waiver_reason`. **The newest maker-checker pattern; the same shape would back an ISO-20000 change/approval workflow.**

### FinanceWorkflowService / SettlementOpsService / PayoutControlService
- **Responsibility**: maker-checker daily close (variance-tolerance gate, fail-closed default), settlement batch close, payout limits + approval queue. **The plan's §3 approval/close patterns — complete.**

## Bottom Line

The attached ISO/domain plan is substantially **already implemented in spirit** for Payments (operations, funds, reconciliation & close), KYC/Customer (compliance risk, KYC docs, identity pilot), Billing (tenancy → usage → outbox → pricing → invoices → completeness gate, V38–V49), and Administration (RBAC-lite, audit chain, feature flags, maker-checker). Plan DoD #1–#6, #9, #13–#14 are fully or mostly met in behavior. What is genuinely **not** done:

1. **Communication as a first-class domain** (DoD #9–#12) — the plan's central addition. SMS is a legacy utility buried inside the transactions god-class; email is an empty interface; WhatsApp/USSD/templates/campaigns/consent/delivery-retry do not exist. Largest net-new build (~3–5+ dev-weeks for a solid core).
2. **Domain packaging** (DoD #1–#2) — `net.citotech.cito.{flat}` → `net.citotech.cpay.{domains}`; frontend `src/features/{domain}` + route-driven navigation.
3. **Architecture guardrail enforcement** (DoD #15) — ArchUnit rules; zero cost today, prevents every future violation.
4. **One payment engine + state machine** (DoD #6, #8) — v1/v2 parity exists but not unity; statuses are free-form strings.
5. **Operations SLI/SLO + incident/problem + service catalogue** (DoD #16–#17) — the ISO/IEC 20000-1 home.
6. **Communication→Billing metering** (DoD #11) — the pipeline exists; it just has no Communication source events yet.

**Recommended first moves (in order):** land the ArchUnit guardrails (P0.1, ~1 day); extract SMS into `communication/` with the `@SchedulerLock` fix (P0.5 — fixes a real double-send bug); define `CommunicationChannelAdapter` + template/preference/delivery core (P0.6); then frontend route-driven navigation (P0.3) and the payment state machine (P0.8). The Billing engine already proves the "do it once, domain-owned, outbox-backed" pattern the plan wants Communication to follow.
